# 0024：实体关系表、图谱可视化与上下文关系注入

2026-10-31 决策，2026-11-01 修订上下文与交互边界。沿用本机单作者、SQLite 唯一权威存储与仅工程验证的授权。复查证据见 [本次 review](../reviews/REVIEW-2026-11-01.md)。

## 背景与痛点

- 当前实体（人物、世界设定、伏笔）仅作为孤立卡片存在，人物间的亲疏、辈分、阵营归属与恩怨情仇只能以非结构化自然语言分散写在档案详情中。
- 在长篇小说中（角色数量超过 20 人），作者容易混淆多方势力博弈与角色人际圈；同时，当多个角色在同一章节出场时，模型缺少显式、成对的结构化人际约束，极易产生角色关系幻觉（如误将生死大敌写成初识路人、把道侣写成普通同门）。
- 项目开发约定（`AGENTS.md`）明确指出：“初版不引入 Redis、独立向量数据库、微服务或自由行动的多 Agent 循环，除非当前任务和实测证据需要。人物关系先用关系表表达。”

## 决策内容

1. **关系存储与数据模型**：
   - 增加 `entity_relations` 表，记录 `(id, novel_id, source_id, target_id, relation_type, description, bidirectional, created_at, updated_at)`。
   - 外键强关联 `novels.id` 与 `entities.id`，并在 `(novel_id, source_id, target_id, relation_type)` 上设置唯一约束，防止重复边。
   - 关系仅允许在同作品内的两个不同实体之间建立，严禁跨作品或自指向关联。
   - Alembic 迁移使用 `1b8c6e431fa7_entity_relations.py`，向下依赖 `f17b6d429ea5`，具备完整 upgrade/downgrade 支持。

2. **写作上下文中的作者关系设定**：
   - `build_context` 从本章命中人物检索一跳邻居，邻居卡片属于可选参考，不能挤掉明确必读或无上限撑大请求。只传入本次实际纳入的两端人物之间的关系；裁剪档案时同步裁剪关系、预览和模型消息。
   - `character_relations` 是作者设定，不是已发生事实。新任务使用 `base-v2.md`，保留方向并要求区分人物知识与叙述者信息；不能据此保证模型不 OOC。旧任务保留冻结的原消息。

3. **前端交互与轻量可视化（Lightweight Graph）**：
   - 保持零第三方重型图表库依赖，采用纯 React + SVG 原生渲染。
   - 在“人物与设定”（`StoryPage`）中新增“关系图谱”视图，以自适应网状拓扑展示全书人物脉络。
   - 节点展示人物圆标与名称；连线根据关系性质色彩区分（情缘/亲善为青粉色、仇敌/对立为绯红色、同门/主仆为墨青色），并标注关系胶囊。
   - 交互上支持点击节点高亮一度人脉、抽屉式快速新增/修改/删除关系；在写作界面的“速查设定”抽屉中同步联动展示当前人物的人际标签。
   - 编辑、删除须携带 `base_updated_at`，冲突保留本页修改并允许比较最新关系；重复类型与空白类型返回明确错误。单向关系从任一端均可查看，箭头保留原方向。
   - 桌面提供 SVG 键盘选择与人物下拉框；手机使用人物选择和关系列表，避免将全书图谱缩成不可读的缩略图。沿用现有工作台，无新主要布局。
