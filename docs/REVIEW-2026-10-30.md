# 2026-10-30：AI 小说项目对照与本轮改进

结论：Inkloom 已有开书、细纲、正文候选、修稿、定稿、记忆和导出的工程主线；更明显的缺口是跨章节规划的可见性、持续讨论能力和真实长篇成稿验证。继续增加生成入口不会自动解决这些问题。本轮先完成故事脉络，让作者能找到并修改具体章节，同时看清伏笔安排和实际进展。

## 核查范围

核查 GitHub 公开介绍、MuMu 的灵感 API 多轮反馈实现，以及 Novelcrafter、Sudowrite 的官方文档；补读 Linux DO 的作者自荐与用户反馈。没有安装竞品、调用它们的模型或比较成稿文学质量。下列 stars 是 2026-10-30 GitHub API 快照，只表示关注度；许可证来自同一 API 元数据，本轮独立实现，不复制竞品组件、提示词或图片。

## 本轮落地

新增 **大纲与章节 → 故事脉络**：按章阅读细纲，区分作者的计划回收、有效正文进展和待复核旧记录；可按卷、章状态、伏笔和关键词定位，打开细纲修改后返回，也可进入对应伏笔档案。40 章一页，手机采用单列和可收起筛选。脉络由现有资料投影，不复制出另一套需人工同步的数据。

独立的 `storyMap.ts` 负责排序、关联有效性和筛选；`StoryMap.tsx` 负责读取与操作，沿用原有 API 和编辑器。没有数据库迁移或真实模型调用。先生成 UI 概念图，再完成页面与浏览器检查。实现和验证见 [故事脉络记录](IMPLEMENTATION-STORY-MAP.md)。

## 距离实际投入使用仍需完成

1. **真实连续十章验收。** 这是投入连载前最重要的证据缺口：同一模型完成写作、审稿、定稿、改前文再续写，记录实际费用、重复、人物失忆和作者返工。用户目前选择只做工程验证，因此本轮没有执行，也不能声称文学质量已过关。
2. **带上下文的持续聊天规划。** 绑定本书及指定卷/章，明确本次发送的资料和历史；建议先进入差异预览，通过现有版本检查采纳。讨论内容不自动成为故事事实。
3. **章内场景与人物状态演变。** 场景应有目的、冲突和结果；人物状态要绑定叙事位置和原文。当前脉络按章节排序，不能代替故事发生时间或完整关系图。
4. **有限多章批次与模型接入覆盖。** 在逐章效果有证据后，再增加预算、检查点和边界暂停。免 Key 本地服务、更多原生协议仍有改进空间；不能用无限重试换取表面成功。后续工程 review 已补齐整次请求及无有效输出时限，并修复规划范围、中文召回、资料预算与目录读取，见 [实现记录](IMPLEMENTATION-CONTEXT-BOUNDARIES.md)。

本轮不以安装难度、stars、自动生成字数或模型自评分宣称优于上述项目；实际目标是缩短作者定位、修改和继续创作的操作路径。
